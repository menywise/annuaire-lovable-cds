# CDS — Référentiel V0

**Validé le 28 septembre 2026.** Ce fichier fixe le périmètre de la V0 : ce qui doit exister, fonctionner à 100 % et être désactivable avant toute duplication.

Règle d'or : **l'existant d'abord, 100 % fiable. On ajoute ensuite, un module à la fois, par itération propre.**

Contraintes :

- Le dépôt reste 100 % compatible Lovable (aucune réécriture d'historique, branche toujours fonctionnelle).
- Pas de crédits Lovable : chaque changement de base est livré en migration dans `supabase/migrations/` **et** exécuté à la main dans l'éditeur SQL. Les migrations sont écrites pour pouvoir être rejouées sans danger.
- Chaque migration est testée en local avant livraison : `tests/db/run.sh` (voir en bas).

## 0. Décisions de cadrage (28 septembre 2026)

- **Destination** : ce dépôt sert à lancer les **projets propres du studio** de création d'entreprise (pas de clients tiers). « Vendable » = chaque projet doit pouvoir être monétisé ou revendu.
- **Règle d'adoption** : on adopte une brique externe (hébergée sur Coolify) seulement si sa valeur dépasse le coût d'un second système (autre compte, autre admin, autre serveur). Sinon, on garde le module dans ce dépôt.
- **Briques externes retenues** (source : `BLUEPRINT_CONSTELLATION_HOLOKAI.md`, 21/08/2026) : Ghost (magazine, newsletter, abonnements payants), Revive Adserver (régie), Umami (audience), Shlink (liens courts), Meilisearch (recherche, quand le volume l'exige). Avant adoption, chaque brique repasse la grille : licence MIT/Apache, Docker, API, dernier commit < 6 mois.
- **Gardés dans ce dépôt** : socle (comptes Supabase partagés, admin, légal, SEO), **forum** (simple, déjà intégré aux membres et à la messagerie ; aucun forum MIT ne partage nos comptes), **annuaire + géographie** et **petites annonces** (aucun équivalent libre mûr).
- **Conséquences** : le module Blog reste minimal (Ghost prend le magazine), la Régie (17) devient un simple emplacement qui affiche une zone Revive, la Mesure d'audience (J) = intégration Umami, pas de code.

## 4. Définition de « fini » pour un module

1. Interrupteur en base, dépendances respectées.
2. Éteint : aucune trace (pages → accueil, menus, pied de page, sitemap, admin).
3. Règles d'accès testées pour visiteur, membre, admin (`tests/db/`).
4. Admin complet : créer, lire, modifier, supprimer, modérer.
5. Chaque page gère chargement, vide, erreur, introuvable.
6. SEO sur chaque page publique.
7. Au moins un test automatique.
8. Ligne cochée dans la grille de conformité.

Échec si : page blanche, erreur console ou JavaScript, réponse 5xx, débordement horizontal, pas de h1, page d'un module éteint accessible, page protégée ouverte à un visiteur. Fonctions réservées à la clé de service. **Clés Stripe en secrets d'environnement uniquement.** Case de renonciation au droit de rétractation (L221-28 13°, reprise de Goldwing) obligatoire, datée avec le paiement. - **Suivi de contacts** : l'écran admin n'affiche et n'exporte plus que des chiffres (par étape, source, mois), plus aucun nom ni e-mail, conformément à l'annonce « le détail reste privé à son propriétaire ».
- **États** : erreurs de chargement affichées sur forum, témoignages, annuaire, annonces, formations, régie, géographie, suivi de contacts ; chargement réel en modération.
- **Composants partagés** : `RecordEditor` (formulaire d'édition décrit par ses champs), `CategoryManager`, `ModerationEditor`/`ModerationControl`, `ModerationNote`, `moveRow` (ordre).

Limites connues : en base, l'admin peut toujours lire le détail des contacts de tous les membres (utile pour une demande RGPD) ; seul l'écran a été restreint. Pas de rôle Modérateur.

### Lot 5 C « Pages libres » — fait (29/09/2026)

Migration `20260929200000_v0_lot5c_pages.sql`, test `test_08_pages.sql`.

- **Règle d'adoption appliquée** : Puck (éditeur de pages React, MIT, `@puckeditor/core` 0.23) étudié. Retenu : son **format de données**, pas encore sa bibliothèque (version 0.x, ~35 dépendances lourdes, et `bun.lock` impossible à régénérer hors Lovable = risque de build cassé). Décision du 29/09 : éditeur maison par formulaires, Puck se branchera plus tard sans migrer les pages (`SECTIONS` a déjà la forme d'une configuration Puck).
- **Module `pages`** (éteint par défaut, sans dépendance) : 21e interrupteur. Éteint = aucune page lisible, même publiée (règle en base), `/pages/…` renvoie à l'accueil, rien dans les menus, le plan du site ou le sitemap.
- **Table `pages`** : titre, adresse, description SEO, contenu `data` au format Puck (`{root, content:[{type, props}]}`), brouillon/publiée, une seule page d'accueil. La base contrôle le format (sections typées, 60 au plus, 256 Ko), l'adresse et le titre ; dates et auteur tenus par la base. Écriture : admin seulement.
- **7 sections** : bandeau d'accueil, texte enrichi, image et texte, points forts, image seule, questions fréquentes (données FAQPage), appel à l'action. Liens et images filtrés (pas de `javascript:`, images en https ou chemin interne). Section inconnue ou vide ignorée : jamais de page blanche.
- **Écran `/admin/pages`** : créer, publier/dépublier, modifier, choisir la page d'accueil, supprimer (confirmation). Éditeur : réglages SEO, sections à ajouter, monter, descendre, retirer, images via la médiathèque, aperçu avant enregistrement, alerte si on quitte sans enregistrer.
- **Accueil** : module allumé **et** page d'accueil publiée → elle remplace l'accueil de démonstration (rendu serveur, SEO depuis la page). Sinon l'accueil de démonstration reste.
- **Pages publiques** `/pages/<adresse>` : rendu serveur, SEO, fil d'Ariane, introuvable géré ; plan du site et sitemap les listent.

Limites connues : les pages n'apparaissent pas encore dans le menu principal (pas d'éditeur de menu) ; pas d'historique des versions ; pas de glisser-déposer (Puck plus tard).

### Lot 4 « Failles des briques 12 à 16 » — fait (29/09/2026)
